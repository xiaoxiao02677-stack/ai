1. **主链路健康**：run_server → server → routes → websocket_handler → conversations → agent → stateless_llm 的分层清晰，模块 #1/#2/#3 的搬移与拆分已在服务器真实部署（git 99c4705 / 0d065c4 / 478dca7），文档行号引用精确可信。

## 6. MemoryStore 分层与 Hermes 接口边界（§6）

### 现状分层（Phase 1A，已部署）
```
MemoryManager / Retriever / memory_panel（17 处）
        ↓
MemoryStore（store.py 兼容门面，25 方法）── stats() ⚠ 直连 provider._conn 执行 raw SQL
        ↓
4 × Repository（memory/state/summary/keyword，互不依赖）
        ↓ 共享单实例（单连接 + 单 threading.Lock）
SQLiteStorageProvider（DDL/行映射/安全文件名）
        ↓
long_term_memory_data/<conf_uid>.db
```

### Repository + StorageProvider 角色评估
- **正确点**：Repository 按领域拆分合理；调用方零改动达成；单连接单锁语义与原版一致；DDL 兼容。
- **最大问题（Hermes 障碍排序）**：
  1. **无抽象 Provider 接口**：4 个 repository 的 `__init__` 类型标注都是具体类 `SQLiteStorageProvider`，且全部直接访问 `provider._lock` / `provider._conn` 私有属性。`storage/__init__.py` docstring 自己承认契约是"非正式的属性级约定"（conf_uid/db_path/_lock/_conn/行映射）。**换存储 = 改 4 个 repository + 门面**，分层名存实亡。
  2. `store.py:128-147 stats()` 绕过 repository 直连 SQL ×3（文档辩解为"跨库聚合属门面职责"，实际是偷懒路径）。
  3. `search_active` 全表加载后内存过滤（无 SQL LIKE 下推）——当前量级（个人助手）无碍，但 Hermes/向量场景会放大。
  4. memory_panel 17 处直接操作 `mgr.store.*`，绕开 MemoryManager（读多写少尚可接受，但 wipe 是 N+1 逐条删）。

### 未来 Hermes 集成的接口边界（只分析，不实现）
目标形态：
```
MemoryManager（零改动）
   ↓
Repository 层（零改动）
   ↓
StorageProvider 协议（方法级：execute / query / close / 事务边界）
   ├─ SQLiteStorageProvider（现实现改名收编）
   └─ HermesProvider（未来，网络存储）
```
前置条件 = 把属性级契约升级为 **方法级 Protocol**（typing.Protocol，静态检查可验证），repository 只依赖协议方法。工作量约一天（4 个 repository + provider + stats 归位 + 41 项自测回归）。**本阶段不做**，但 §10 的 B2 就是它。

## 7. Agent / Conversation ↔ Memory 耦合实测（§7）

### 全量接触点（file:line 均已核实）
| # | 位置 | 内容 | 性质 |
|---|---|---|---|

| 4 | `agent/agents/basic_memory_agent.py:142` | `self._llm = llm`（`_set_llm`）——`_llm` 属性契约源头，由 `agent_factory.py:59-86` 创建 | 属性名契约 |

### 检查结论
- **Agent 直接摸 MemoryStore？** 无。agent/ 目录零 LTM import（全仓 grep 实证：LTM import 只在 single_conversation.py 和 long_term_memory/ 内部）。
- **Conversation 摸 SQLite？** 无。全部经模块级 `ltm.build_retrieval_context / extract_from_turn`。
- **冗余多层调用？** 仅一处小冗余：`_should_inject_summary` 导致 `get_summary` 每轮读两次库（manager.py 内部）。其余每一跳都有实义。
- **群聊无 LTM**：group_conversation.py 零引用（grep 实证），单/群能力不一致，登记即可。
- **两个契约隐患**（不阻塞，登记）：
  1. `_llm` 是**属性名契约**（agent.md:54 已书面备案"属性名必须保留"）——脆弱但已有文档；
  2. `metadata["ltm_context"]` / `metadata["skip_memory"]` 是跨 3 层（conversation → BatchInput → prompt_assembler）的**无类型 dict 约定**——建议下一阶段定义 dataclass（不改运行时行为）。

### 反向依赖（本节最重要的发现）
LTM → agent 的依赖（`__init__.py:308` import LLMFactory + `_resolve_chat_llm_config` 直读 conf.yaml）把"LTM 是叶子"的架构方向打穿了。这是 §9 P1-1、§10 B4 的根源。
