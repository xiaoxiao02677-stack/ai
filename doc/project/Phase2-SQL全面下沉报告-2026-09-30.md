## 一、目标与停止条件

**目标**：把 Phase 1B 遗留的"SQL 形态契约"改造为"领域聚合形态契约"，使**换存储后端 = 只改组合根一行**（Hermes 前置条件彻底达成）。

Phase 1B 结束时的状态：业务层（manager/retriever/extractor/deduplicator）已零 SQL，但 `StorageProvider` 协议本身是 5 个 SQL 原语（`execute(sql)` / `query_one(sql)` / `query_rows(sql)` / `transaction()` / `row_to_memory_record(row)`），4 个 repository 仍在拼 SQL 字符串。SQL 没有泄漏，但**契约泄漏**——换后端仍要重写 4 个文件。

**停止条件（全部未触发）**：
- MemoryStore 21 个公开方法签名：零变化
- 4 张表 DDL：逐字节不变（存量 .db 零迁移）
- 对外行为：1B↔2 逻辑数据库对拍逐字段一致
- conversation 层 / memory_panel.py：零改动（git status 里没有它们）

## 二、改动前结构（Phase 1B 终态）

```
manager/retriever  →  store.py（门面）
                        └─ 4 个表仓储（memory/state/summary/keyword_repository.py）
                              └─ provider.py 协议（5 个 SQL 原语）★契约是 SQL 形态
                                    └─ sqlite_provider.py（连接/DDL/锁）
```

问题：repository 是"SQL 代理"——每个方法都在拼 SQL 字符串。SQL 集中在 storage/ 内没错，但协议原语以 `sql: str` 为参数，后端方言绑死在 4 个 repository 文件里。

## 三、改动后结构（Phase 2 终态）

```
manager            →  store.py（门面 + 组合根，唯一 import 具体 provider 处）
retriever          →  MemoryRepository + KeywordRepository（直接依赖领域仓储）
store.py ─┬─ MemoryRepository  ──┐
          ├─ KeywordRepository ──┤ repository.py（领域规则：updated_at 盖章、
          ├─ StateRepository   ──┤   关键词规范化、内存命中排序）——零 SQL
          └─ SummaryRepository ──┘
                    ↓ 全部依赖
          provider.py StorageProvider 协议（19 个聚合方法，领域对象进出）★契约是领域形态
                    ↓ 唯一实现
          sqlite_provider.py（连接/DDL/锁/全部 28 条 SQL/行↔对象映射）
```

**依赖方向铁律**：`sqlite_provider` / `SQLiteStorageProvider` 只被 `storage/__init__.py` 和 `store.py`（组合根）提及；`store.py` 只被 `manager` / `__init__` / `run_tests` 引用；retriever 不再依赖门面。

## 五、关键技术决策

1. **协议聚合化而非 CRUD 泛化**：19 个方法按聚合（memories/keywords/user_state/summary）分组，每个方法语义自明（`mark_used` 而非 `execute("UPDATE …")`）。拒绝泛型 CRUD（`save(obj)`/`find(criteria)`）——那会把领域语义推回调用方。
2. **`save_memory` 单写入口**：INSERT OR REPLACE 语义（memory_id 为主键）使 add/update 天然合一；`update_memory` 的"盖 updated_at"是领域规则留在 repository。
3. **bump_turn_count 原子性内化**：Phase 1B 用 `transaction()` 原语在仓储里组 UPSERT+回读；Phase 2 该组合直接是 provider 的一个方法，原子性成为实现细节，调用方不可见。
4. **search_active 排序留在 repository**：命中排序是对 MemoryRecord 字段的内存计算（领域规则），provider 只负责 `list_memories(status="active")`。将来 Hermes 可整体下推，语义不变。
5. **`PRAGMA busy_timeout=10000`**：实测发现"每线程独立连接写同一 DB"（面板 + 会话双开场景）在默认 5s 超时下报 `database is locked`。连接级 PRAGMA，不动 DDL，单连接快路径零影响。
6. **MemoryStore 继承 MemoryRepository**：门面 21 方法里 9 个 memories 方法通过继承获得，消除纯转发样板；组合根职责（wire 4 仓储 + 1 provider）不变。

## 八、过程记录与坑

| # | 坑 | 解法 |

| 1 | `ssh_put.py` 报 `FileNotFoundError [Errno 2]`，但 SFTP listdir 正常 | **Git Bash MSYS 路径转换**把 `/tmp/...` 改写成 Windows 路径传进 argv。`export MSYS_NO_PATHCONV=1` 后恢复。（ssh_run.py 不受影响：整条命令含空格不触发转换） |
| 2 | 本地 mktemp 建的 `/tmp/...` 路径 rm 时被沙箱拦截 `embedded drive prefix` | 改用项目内 `.localtest/` 目录 |
| 3 | smoke 首跑 5 失败：①FakeProvider 漏 `_ck()` ②对拍两栈共用 conf_uid 写同一 .db ③并发 `database is locked` | ①补检查 ②分用 eq_1b/eq_2 + dump 归一化 conf_uid/memory_id ③`PRAGMA busy_timeout=10000` |
| 4 | 服务器 E2E 日志 0 字节 | `uv run python` stdout 全缓冲；沿用 Phase 1B 经验：setsid 后台 + 轮询日志文件 |
| 5 | pkill 与后续命令同会话执行导致 SSH 通道中断 | 拆成两次 ssh_run |
| 6 | `MemoryRetriever` 饥饿扩展需要 keywords 聚合，但主依赖是 MemoryRepository | 构造器加可选 `keywords` 参数 + `getattr(repo, "keywords", None)` 回退，旧签名完全兼容 |
